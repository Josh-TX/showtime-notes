# Detailed decisions (session addendum, see notes.txt for base glossary/architecture)

## Listener -> Server audio transport
Raw PCM only, no codec (Opus/AAC add encode/decode latency, not worth it for sub-500ms target).
Mono, Int16, 48kHz capture via AudioWorklet. Chunked at 20ms (960 samples = 1920 bytes/chunk).
Binary WS message per chunk: [seq: uint32][timestamp: uint32][PCM Int16 samples].
Server relays chunks unmodified to any subscribed live-audio client (no transcoding).
Client playback: push Int16 samples into a ring buffer read by an AudioWorkletProcessor (no MSE, no scheduled AudioBufferSourceNode). Underrun = silence, overflow = drop oldest.
Known risk: WS rides TCP, so packet loss causes head-of-line blocking/stalls (not an issue on LAN; would matter on flaky venue wifi).

## Buffer
Single unified rolling buffer, ~1 second, serves two purposes:
- Recording pre-roll: starting a recording has an option to include the previous 1s (so the user can wait to hear the first note before clicking record, and still capture it). Also communicates the feature exists.
- Chroma FFT window lookback (window duration is well under 1s even before halving, so this buffer already covers it - no separate buffer needed).

## Recording
Held in memory only; a server crash losing an in-progress take is accepted as correct behavior (partial takes are useless, no cleanup needed).
Continues across all-client-disconnect (server-side state, not tied to any client's websocket).
Capped at 20 minutes; rotates out (drops) oldest chunks past that.
On stop: user must name/confirm the recording via a small form before processing (Demucs/beat_this) starts.
Separate explicit "discard recording" action exists (throws away a take immediately, no naming/processing).

## Processing pipeline
Wrap raw PCM in a WAV header (free, no encode) instead of routing through mp3/opus first.
Feed that WAV directly to both Demucs and beat_this - both read WAV natively via torchaudio/soundfile, confirmed against showtime-notes-research (ffmpeg is only needed there because the source was compressed .webm, not because either tool requires it).

## Persisted storage (post-processing)
The 3 resulting files (original recording, vocals, novocals) get transcoded via ffmpeg to AAC (not Opus) for storage/playback - AAC has far better native browser <audio>/playback compatibility than Opus (Safari issues), and the storage use case cares about compatibility more than best-possible compression.
Target ~64-96kbps mono (not fixed exact number) - sufficient for the actual use case (listening back to identify cues/notes, not critical listening). 128kbps considered near-transparent if quality issues show up in practice.
Source WAV/raw PCM discarded once the AAC transcode is done.

## Waveform peaks
Kept as a precomputed server-side step (not client-side decode-and-compute from the AAC file), even though client-side decode via decodeAudioData would be fast enough at ~5MB/64kbps files - precomputing during the processing pass is already free and gives instant waveform render.
Storage format: JSON (plain text floats), not binary - ~150KB per 10-min song, negligible either way.

## Chroma / sync feature computation
PCM buffer feeds directly into the existing ChromaStream-style incremental design (already built for "any chunk size" streaming) - no architecture change needed, just format adaptation:
- Convert Int16 -> float32.
- Resample 48kHz capture -> 22050Hz (whatever SR the feature pipeline expects).
FFT window (N_FFT) is being halved vs. the research project's offline value, per the user's own prior aligner-cli testing - single unified mechanism, no separate fast/slow (RMS-onset + chroma) two-tier detection.
No persistent multi-second raw-audio buffer is needed for chroma itself - ChromaStream only retains the unconsumed tail needed to complete the next FFT window (confirmed in chroma.py), then keeps only the tiny resulting feature vectors.

## Sync/align triggering
Aligning is never automatic by default - a user must explicitly tell the server to align with a specific song.
Once synced and a song ends, autoplay still applies: automatically moves to acquiring-sync on the next song in show order.
Two acquire modes:
- acquire-sync-start: scans only the first ACQUIRE_START_RANGE seconds of the reference song (default 20s, configurable/toggleable). This is the common case.
- acquire-sync-middle: user scrolls the Timeline Container to the desired region and hits "sync here" - the current viewport is the scan range (not drag-select, not manual numeric input).
Acquiring-sync never times out on its own - keeps re-scanning indefinitely until it locks or the user changes target.
Selecting a new align target while already acquiring/synced on another song immediately cancels the old one and starts the new one (last request wins).
A separate explicit "stop sync" action exists to return to no-target/ready state without picking a new song.

## Position broadcast / client rendering
Server pushes an absolute position update every chroma frame (~50ms - matches feature hop size), client assumes live tempo matches the reference (no client-side tempo extrapolation).
Client does not snap to each new position - eases from current rendered position toward the new target over a fixed SMOOTHING_DURATION of 200ms.

## Confidence bars
Server broadcasts a "confidence_bars" message every frame: list of candidate reference-frame positions and their scores (matches the research project's existing "candidates"/"debug_anchors" messages almost exactly, just renamed/formalized).
Sent during acquiring-sync (full scan range's candidates).
Also sent during synced/tracking, limited to a +/-3 second window around the current locked position (not just as an early-warning-on-confidence-drop signal - always shown).
Client renders these on the Timeline.

## Live audio "listen" feature (separate from the above chroma path)
Two tiers:
- Loudness levels: a lightweight scalar broadcast to all connected clients at all times, shown in the navbar (cheap, always-on).
- Full audio playback: opt-in only, via a navbar dropdown "play live audio" action - not streamed to a client unless they've explicitly requested it. Rarely-used feature.
No special backpressure handling for a lagging live-audio-listen subscriber (no drop/disconnect logic) - rare feature, natural WS/TCP buffering is fine.
